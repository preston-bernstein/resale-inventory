judgment pass across three lenses (Elegance/Architecture/DRY, dead-code &

plus trivial NITs; one item is escalated below, not applied. Regression net:

## Applied — Duplication (fallow `dupes`, DRY lens)

Went from 29 to 26 fallow clone groups (see Escalated below for why the
remaining ones are untouched, not missed):

- `app/api/auth/login/route.ts` and `signup/route.ts` duplicated the same
  2-line "coerce `body.email`/`body.password` to strings" block. Extracted
  `parseEmailPassword()` into `lib/apiRequest.ts`, alongside its sibling
  request-parsing helpers (`parseJsonBody`, `parseItemId`, etc.) — same file,
  same convention, both routes now call it.
- `app/api/items/suggestions/route.ts` ran the identical frequency-sorted
  `SELECT ... FROM <table> WHERE tenant_id = ? AND <field> ...` query against
  `clothing_details` and `book_details`, differing only by table name.
  Extracted `fieldSuggestions(table, field, tenantId)`; `table` is one of two
  literals and `field` is only ever a value already checked against
  `CLOTHING_FIELDS`/`BOOK_FIELDS` before the call, so the interpolation stays
  exactly as safe as before.
- `lib/pairingToken.ts#createToken` and `lib/tenantAuth.ts#createSession`
  independently generated the same shape of opaque bearer token (32 random
  bytes → hex, SHA-256 hash, uuid id, `Date.now()` + TTL) — both files even
  had comments cross-referencing the other as "mirrors ... exact hashed-token
  idiom." Extracted `hashToken()` + `generateOpaqueToken(ttlMs)` into a new
  `lib/opaqueToken.ts`; both call sites now call `generateOpaqueToken` and
  import `hashToken` for their token-lookup call sites. `crypto`/`uuidv4`
  imports kept in both files where still used for other things (scrypt,
  `timingSafeEqual`, tenant id generation).
- `components/PhotoUpload.tsx`'s `handleUpload`/`handleDelete`/`handleMove`
  each repeated the same fetch → ok-check → parse-error → catch → reset-busy
  shape. Extracted `requestPhotoUpdate(requestFn, actionName)`; also folds in
  the observability fix below (was three separate empty-ish `catch {}`
  blocks, now one place that logs).

## Applied — Observability (silent-failure lens)

Of 67 deterministically-flagged catch blocks, the large majority were
legitimate by inspection (client-side UI error states already surfacing to
the user; documented best-effort fallbacks like the dark-mode no-flash
inline script's `catch (e) {}`, `lib/connectors/apiFetch.ts`'s "not JSON,
fall back to raw text," `middleware.ts`'s malformed-origin handling; health
detail returns from `checkConnectionHealth` implementations; two calls that
turned out to already log via a mapper function my regex couldn't see through
— `mapPatchDbError`/`mapImportDbError`). Two were genuine gaps and two dozen
were UI states silently invisible to server logs / the browser console:

- **`app/api/export/route.ts`** — the outer `catch` returned a bare 500 with
  zero trace of what failed. Added `console.error('GET /api/export error:',
  err)`, matching the convention every sibling route already follows.
- **`app/api/connections/[id]/first-win/route.ts`** — the health-check
  `catch`'s `else` branch (an unexpected, non-`ConnectorNotConfiguredError`
  failure) discarded `err` entirely before returning a generic "health check
  failed" string. Added a `console.error` in that branch only (the expected
  `ConnectorNotConfiguredError` case stays unlogged — it isn't a bug).
- 15 client-side catch blocks across `app/inventory/page.tsx`,
  `app/inventory/[id]/page.tsx` (×3), `app/phone/[token]/page.tsx` (×2),
  `components/useAuthForm.ts`, `components/AddBookForm.tsx`,
  `components/useSubmitItemForm.ts`,
  `components/connections/{ConsentScreen,ConnectionsView,StatusRow,
  FirstWinPanel}.tsx`, `components/connections/CredentialStep.tsx` (×2), and
  `components/PhotoUpload.tsx` (×3, via the DRY extraction above) each set
  UI-visible error state but never logged the underlying error anywhere —
  fine for the operator watching the screen live, useless for reconstructing
  what happened from a bug report. Added a `console.error(...)` alongside
  each `setError`/`setXError` call. `CredentialStep.tsx`'s two catches handle
  credential-bearing forms; the added logs print only the caught error object
  (a fetch/parse failure), never the request body, consistent with that
  file's own existing "never log `credential`" comment.

## Escalated — not applied

**`lib/connectors/{depop,grailed,mercari,poshmark,swappa,amazon,ebay,etsy}.ts`
duplication** (19 of the 26 remaining fallow clone groups, ~1,000 of the
1,066 duplicated lines fallow reports). These are the Playwright-driven
marketplace connectors; fallow's clone-family view suggests concrete
extractions (e.g. 105 shared lines across
depop/grailed/mercari/poshmark/swappa's `updateListingAction`/photo-upload/
listing-id-extraction scaffolding). Not auto-applied here because:

1. Every one of these connectors is explicitly documented in its own
   docstrings as "best-effort... not confirmed against a live account" —
   selectors and per-platform quirks are unverified against the real sites,
   so the only real regression signal available is the existing
   `lib/connectors/__tests__/*.test.ts` mock-based suites, not a live
   integration check.
2. `.fallowrc.json` already documents the maintainer weighing this exact
   trade-off once, for a smaller case (the `phone-session`/`photos` route
   handler clone), and choosing directness over a shared wrapper — "judged
   not worth trading directness for." A template-method extraction across
   6-8 platform files with materially different selectors, field sets, and
   error text is the same trade-off at much larger scale, and would need its
   own dedicated review pass (ideally live-account-verified per platform) to
   apply with confidence rather than as one item in a general polish pass.
3. `.fallowrc.json`'s `ignoreExports` block already carves out a related,
   deliberate exception for these same 8 files' raw per-method exports
   (kept individually exported only so each connector's own test file can
   unit-test them by name).

Recommendation if/when picked up: a per-connector-family PR (e.g. just the
5 Playwright-scraper connectors, not the 2 REST-API ones — ebay/etsy's
duplication is much smaller and lower-risk to fix on its own), verified
against each connector's existing mocked test suite plus a live-account spot
check before merge.
